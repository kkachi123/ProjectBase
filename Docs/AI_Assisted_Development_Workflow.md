# AI 협업 개발 절차

AI와 요구사항·설계를 협의하고, 실제 코드와 동작을 확인하며 개발하는 작업 절차다. 반복 작업은 Guide로 표준화하고, 작업별 판단과 결과는 Log에 남겨 다른 AI가 이어서 작업할 때도 개발 방향을 유지한다.

**요구사항 확정 → 현재 구현 조사 → 분석·설계 협의 → 계획 작성·검토 → 단계별 구현 → 코드·설정 검증 → 실제 동작 검증 → 문서 정리·인수인계·커밋**

## 1. 요구사항과 작업 범위 확정

- 구현할 동작과 완료 조건을 정한다. 정상 실행뿐 아니라 취소·중단·종료 후 동작도 필요한 범위에서 확인한다.
- 유지할 기존 기능과 이번에 변경하지 않을 영역을 구분한다.
- 분석·의견 제시, 계획 작성, 구현 중 어디까지 요청된 작업인지 확인한다. 분석 요청만으로 코드를 수정하지 않는다.
- 결과에 영향을 주는 미확정 사항은 사용자에게 확인한다. 사소한 구현 세부사항까지 모두 질문하지는 않는다.

결과: 무엇을 만들고 무엇은 바꾸지 않을지 명확한 작업 범위.

## 2. 현재 코드와 연결 관계 조사

- [프로젝트 작업 지침](Skill/AGENTS.md)과 해당 작업에 적용되는 Guide를 읽는다.
- Git 변경사항을 확인하여 기존 사용자 작업과 이번 작업을 구분한다.
- 대상 클래스의 호출처·의존성·초기화·실행·종료 흐름을 확인한다.
- 필요한 경우 State·Transition·Handler·SO와 Prefab·Animator·Animation Event의 연결도 확인한다.
- 기존 기능으로 해결할 수 있는지, 새 코드가 필요한지, 대체 후 제거할 코드가 무엇인지 파악한다.

과거 대화나 Log만으로 현재 구현을 단정하지 않는다. 실제 소스와 에셋을 확인하고, 확인한 사실과 가정을 구분한다.

결과: 현재 동작과 변경 영향 범위에 대한 근거.

## 3. 문제 분석과 설계 방향 협의

- 현재 문제의 원인을 실제 호출 순서와 책임 배치로 설명한다.
- 사용자 제안도 그대로 수용하지 않고 장점·허점·기존 기능에 미치는 영향을 확인한다.
- 공통 책임과 개체별 책임, 데이터와 실행 상태, 판단과 실행의 경계를 정한다.
- 더 단순한 대안이 있으면 비교한다. 미래 재사용 가능성만으로 기반 클래스·인터페이스·프레임워크를 늘리지 않는다.
- 사용자가 결정해야 할 동작과 AI가 구현 과정에서 정할 수 있는 세부사항을 구분한다.

예를 들어 기능을 Handler로 옮길 때는 클래스 추가 여부만 정하지 않고, 어떤 처리를 옮기며 State에는 무엇을 남기는지까지 합의한다.

결과: 구현할 구조와 그 구조를 선택한 이유.

## 4. 실행 가능한 계획 작성·검토

[Plan 가이드](Skill/Plan_Guide.md)에 따라 다음 내용을 정리한다.

- 목표와 변경·제외 범위.
- 추가·변경·삭제할 클래스와 책임, 주요 API 및 호출 흐름.
- 의존성을 고려한 구현 순서.
- 기존 설정·직렬화 값·에셋 참조의 이전 방법.
- 컴파일·연결 확인과 실제 동작 검증 기준.

계획서는 논의 기록을 나열하는 문서가 아니라 다른 AI가 읽어도 같은 방향으로 구현할 수 있는 작업 명세로 작성한다. 검토 중 변경된 결정은 본문에 반영하고, 폐기한 안을 현재 구현 대상으로 남기지 않는다.

결과: 구현과 검증을 진행할 기준 문서.

## 5. 단계별 구현

합의한 계획의 의존성에 맞춰 작업을 나눈다. 일반적인 순서는 다음과 같다.

1. 데이터와 필요한 계약 정리.
2. Handler·전략 등 실제 기능 구현.
3. State·Transition 연결.
4. Controller 초기화와 의존성 주입 연결.
5. SO·Prefab·Animator·Animation Event 설정.
6. 참조 전환이 끝난 기존 코드와 불필요해진 연결 제거.

- 연결이 완성되는 단위마다 컴파일과 참조를 확인한다.
- 기존 사용자 변경을 보존하고, 요청과 무관한 코드·주석·서식을 함께 수정하지 않는다.
- 과도한 예외 검증·반복 null 체크·사용하지 않는 확장 지점은 추가하지 않는다.
- 함수 설명은 필요한 곳에 짧은 한국어 단답형 주석으로 작성한다.
- 계획의 전제가 틀리거나 범위 확대가 필요하면 이유와 선택지를 설명하고 방향을 확인한다.

Unity 에셋은 Editor API로 변경한다. 미저장 씬을 임의로 저장·재로드하지 않고, GUID·설정값·Prefab Override를 보존한다.

결과: 계획한 책임과 연결을 갖춘 구현.

## 6. 코드·설정 검증

- 컴파일 오류, 삭제된 타입·API 참조, Missing Script를 확인한다.
- 초기화·실행·종료 순서와 이벤트 구독·해제, 중단 시 정리를 확인한다.
- 중복 상태 저장·불필요한 전달 함수·반복 갱신 중 Component 검색 여부를 확인한다.
- SO·Prefab 참조, Animator 전이 조건, Animation Event의 함수·인자를 확인한다.
- 변경된 코드와 설정이 계획 범위에 해당하며 기존 사용자 작업을 침범하지 않았는지 확인한다.

Editor 연결 등으로 설정을 완료할 수 없다면 즉시 남은 작업을 알린다. 사용자가 수정할 정확한 에셋·Inspector 위치·설정값을 안내하고, 연결되지 않은 상태를 구현 완료로 보고하지 않는다.

결과: 코드 작성 완료와 에셋 연결 완료 여부가 구분된 검증 결과.

## 7. 사용자 조작을 통한 실제 동작 검증

검증을 시작하기 전에 다음 내용을 먼저 안내한다.

- 확인할 상황과 테스트할 씬·대상.
- 사용자가 수행할 조작.
- 정상일 때 기대되는 결과.

사용자가 직접 조작하는 동안 현재 State·Animator·Console 등 필요한 정보를 확인한다. 정상 흐름뿐 아니라 반복 실행, 피격·사망 중단, 대상 상실, 재활성화처럼 관련 경계 상황도 검증한다.

- 동작을 강제로 만들거나 측정하기 위한 임시 Verification 코드는 작성하지 않는다.
- 실패하면 관찰한 상태와 원인에 근거하여 수정하고 해당 상황을 다시 검증한다.
- 확인하지 못한 동작은 미검증·수동 확인 대기로 명시한다. 컴파일 성공을 실제 동작 성공으로 표현하지 않는다.

결과: 관찰한 정상 동작, 발견한 문제, 남은 검증 항목.

## 8. Guide·Log 정리와 인수인계·커밋

### 반복 작업은 Guide로 표준화

- [ProjectSkill](FSM/ProjectSkill/)처럼 공통 작업 절차를 모으는 위치에 Guide를 작성한다.
- 반복되는 구현·설정·검증 작업에서 확인할 소스, 작업 순서, 에셋 설정, 주의사항을 정리한다.
- 기존 Guide로 충분하면 새 문서를 늘리지 않고 보완한다. 구조가 바뀌면 관련 Guide도 갱신한다.
- 현재 사용하지 않는 절차를 현행 Guide처럼 남기지 않는다.

Guide는 반복 작업의 조사·설정 누락을 줄이고, 다른 AI도 같은 기준으로 작업하도록 돕는다.

### 작업마다 Log에 판단과 결과 기록

Log에는 단순한 파일 변경 목록뿐 아니라 다음 내용을 남긴다.

- 작업 목적과 개발 의도.
- 선택한 구조와 선택 이유, 중요한 제외 범위.
- 실제 변경한 책임·API·호출 흐름과 관련 파일.
- 확인한 결과와 미검증 항목, 필요한 수동 작업.
- 중단한 작업은 현재 진행 지점과 남은 작업, 다음 판단에 영향을 주는 결정.

기존 주제별 Log가 있으면 해당 항목에 이어서 기록한다. 과거 판단은 이력으로 구분하고, 폐기한 설계가 현재 지시로 오해되지 않도록 정리한다.

다른 AI는 Log를 판단 근거로 참고하되, 현재 소스와 최신 사용자 지시를 함께 확인한다. 이를 통해 이미 합의한 방향의 누락, 폐기한 구조의 재도입, 완료 상태에 대한 잘못된 추측을 방지한다.

### 마무리

- 변경 요약, 검증 결과, 남은 작업을 사용자에게 전달한다.
- 실제 완료된 Plan은 필요한 결정·결과를 Log와 Guide에 반영한 뒤 제거한다. 구현이나 검증이 남았다면 완료로 처리하지 않는다.
- Git diff를 확인하고 요청받은 경우에만 지정된 범위와 제목으로 커밋한다. 다른 변경사항은 포함하지 않는다.

결과: 현재 구조에 맞는 Guide, 작업 근거를 보존한 Log, 이어서 작업할 수 있는 인수인계 정보.

## 문서 역할 구분

| 문서 | 목적 | 관리 기준 |
| --- | --- | --- |
| Plan | 이번 작업의 범위·구현 순서·검증 기준 | 진행 중 갱신하고 실제 완료 후 제거 |
| Guide | 반복 작업의 표준 절차 | 현재 구현에 맞춰 유지·보완 |
| Log | 개별 작업의 판단 근거·변경 결과·남은 작업 | 필요한 이력을 보존하고 현행·과거 상태 구분 |

작업 규모에 맞춰 절차를 조절한다. 단순한 변경까지 매번 긴 계획서나 새 Guide를 만들 필요는 없지만, 범위 확인·검증·작업 기록은 생략하지 않는다.
