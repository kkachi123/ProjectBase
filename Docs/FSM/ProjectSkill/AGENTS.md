# AGENTS.md

Codex가 코딩할 때 흔히 저지르는 실수를 줄이기 위한 행동 지침입니다. 필요에 따라 프로젝트별 지침과 함께 적용하세요.

**절충점:** 이 지침은 속도보다 신중함을 우선합니다. 사소한 작업에서는 상황에 맞게 판단하세요.

## 1. 코딩 전에 생각하기

**추측하지 마세요. 혼란을 숨기지 마세요. 선택에 따른 장단점을 드러내세요.**

구현하기 전에:
- 가정한 내용을 명확히 밝히세요. 확실하지 않으면 질문하세요.
- 여러 해석이 가능하다면 모두 제시하세요. 말없이 하나를 선택하지 마세요.
- 더 간단한 접근법이 있다면 알려주세요. 필요하다면 이견을 제시하세요.
- 불명확한 부분이 있다면 멈추세요. 무엇이 혼란스러운지 밝히고 질문하세요.

## 2. 단순함 우선

**문제를 해결하는 데 필요한 최소한의 코드만 작성하세요. 추측에 기반한 코드는 추가하지 마세요.**

- 요청받은 범위를 넘어서는 기능을 추가하지 마세요.
- 한 번만 사용하는 코드를 위해 추상화를 만들지 마세요.
- 요청하지 않은 "유연성"이나 "설정 기능"을 추가하지 마세요.
- 발생할 수 없는 상황을 위한 오류 처리 코드를 추가하지 마세요.
- 50줄로 작성할 수 있는 코드를 200줄로 작성했다면 다시 작성하세요.

스스로 질문하세요. "숙련된 엔지니어가 이 코드를 지나치게 복잡하다고 평가할까?" 그렇다면 단순화하세요.

## 3. 필요한 부분만 변경하기

**꼭 필요한 부분만 수정하세요. 자신이 만든 문제만 정리하세요.**

기존 코드를 수정할 때:
- 인접한 코드, 주석, 서식을 "개선"하지 마세요.
- 문제가 없는 코드를 리팩터링하지 마세요.
- 자신의 방식과 다르더라도 기존 스타일을 따르세요.
- 작업과 무관한 미사용 코드를 발견하면 언급하세요. 삭제하지 마세요.

자신의 변경으로 미사용 코드가 생겼을 때:
- **자신의 변경 때문에** 사용되지 않게 된 import, 변수, 함수를 제거하세요.
- 요청받지 않았다면 기존에 있던 미사용 코드를 제거하지 마세요.

판단 기준: 변경한 모든 줄은 사용자의 요청과 직접 연결되어야 합니다.

## 4. 목표 중심 실행

**성공 기준을 정의하세요. 검증될 때까지 반복하세요.**

작업을 검증 가능한 목표로 바꾸세요.
- "입력 검증 추가" → "잘못된 입력에 대한 테스트를 작성한 뒤 통과시키기"
- "버그 수정" → "버그를 재현하는 테스트를 작성한 뒤 통과시키기"
- "X 리팩터링" → "변경 전후에 테스트가 통과하는지 확인하기"

여러 단계로 이루어진 작업에서는 간단한 계획을 제시하세요.
```
1. [단계] → 검증: [확인 항목]
2. [단계] → 검증: [확인 항목]
3. [단계] → 검증: [확인 항목]
```

명확한 성공 기준이 있으면 스스로 반복 작업을 진행할 수 있습니다. 모호한 기준("작동하게 만들기")은 계속해서 추가 확인을 요구합니다.

---

**이 지침이 효과를 내고 있다는 징후:** diff에 불필요한 변경이 줄어들고, 과도한 복잡성 때문에 다시 작성하는 일이 줄어들며, 실수가 발생한 뒤가 아니라 구현 전에 확인 질문을 하게 됩니다.
